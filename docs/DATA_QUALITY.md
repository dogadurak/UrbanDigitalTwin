# Data Quality & Coordinate Validation — BDG2

Generated by `app/data_engineering/build_dataset.py`. Machine-readable outputs:
`data/processed/manifest.json`, `meter_quality_report.csv`, `sites.csv`.

Source: Building Data Genome Project 2, electricity meter, 2016–2017 hourly.

---

## 1. Coordinate validation

BDG2 publishes **site centroids, not building locations**. All 305 `Rat`
buildings share `38.903504 / -77.005349`. This sets a hard ceiling on any
spatial claim that the building count hides:

| Quantity | Value |
|---|---:|
| Sites in metadata | 19 |
| Sites with coordinates | 15 |
| Sites usable for spatial joins | **14** |
| Distinct coordinate pairs | **14** |
| Buildings total | 1636 |
| Buildings at a spatially usable site | 1363 |

**Any satellite or OSM variable can take at most 14 distinct values across this
dataset.** The effective sample size for a spatial hypothesis is 14, not 1636.
This is why a second dataset with per-building coordinates (NYC LL84 / DC BEPS)
is on the roadmap: BDG2 alone cannot carry a spatial claim.

### Findings

| Site | Status | Detail |
|---|---|---|
| Bobcat, Eagle, Gator, Swan | `missing` | no coordinates in metadata (237 buildings) |
| Wolf | `timezone_mismatch` | timezone `Europe/Dublin` implies `lng=6.2603` outside `[-11.0, -5.0]` |

#### The Wolf longitude sign error

`Wolf` is recorded at latitude **53.3498**, longitude **+6.2603**, timezone
**Europe/Dublin**. Dublin is at **−6.2603**. The latitude is correct and the
longitude magnitude matches exactly; only the sign differs. `+6.2603, 53.3498`
falls in the North Sea off the Dutch coast.

This matters concretely for Sprint 2: sampling Landsat LST or Sentinel-2 NDVI at
the published coordinate would return **water pixels**, and those values would
then be presented as the urban context of 36 buildings.

The check that finds it uses no external data — it cross-examines the dataset's
own `timezone` column against its own coordinate columns, per
`bdg2_metadata.TIMEZONE_BANDS`.

**The coordinate is not silently corrected.** `Wolf` is marked
`spatial_ready = False` and excluded from spatial use; its 36 buildings keep
their energy data, which is unaffected. Editing published coordinates in place
would replace a recorded doubt with an unrecorded assumption.

## 2. Meter series screening

Screening runs before the train/test split and uses no test-period statistics,
so it cannot leak. Thresholds are named constants in `data_quality.py`.

| | Buildings |
|---|---:|
| Screened (electricity columns) | 1578 |
| **Usable** | **1381** |
| Excluded | 197 |

### Exclusion reasons

| Reason | Count |
|---|---:|
| >25% of hours inside stuck/zero runs | 107 |
| More than 50% of the record missing | 61 |
| Fewer than 4380 valid hours | 23 |
| No valid readings at all | 6 |

### Residual risk in the kept set

| | Value |
|---|---:|
| Kept buildings with a flatline run ≥24 h | **324** |
| Kept buildings with a zero run ≥24 h | 0 |
| Median missing fraction among kept | 0.8% |
| Hours flagged as MAD outliers (kept, not dropped) | 192,578 |

324 kept buildings contain at least one 24-hour stuck-meter run but stay under
the 25% bad-run budget. They are flagged, not removed. Outlier hours are
flagged and retained because genuine demand peaks are exactly what an anomaly
detector must learn — dropping them would be circular.

## 3. EUI normalisation — measured effect

The yardstick: **R² obtainable by predicting each building's constant mean.**
No model, no weather, no spatial input. Any model that does not clearly beat
this number has demonstrated only that it knows which building it is looking at.

Measured on the 2017 test split, 1381 buildings, 11.6 M rows:

| Target | Building-identity R² | Scale spread (p99/p01) |
|---|---:|---:|
| `meter_reading` (absolute kWh) | 0.8128 | 1102× |
| **`eui_wh_m2`** (Wh/m²/h) | **0.7292** | **216×** |
| `log1p(meter_reading)` | 0.8871 | — |
| `log1p(eui_wh_m2)` | 0.8054 | — |

### Three honest conclusions

**1. EUI normalisation helps, but far less than expected.** The Sprint 1 plan
predicted this figure would fall below 0.35. It fell from 0.8128 to 0.7292.
The prediction was wrong and is recorded as wrong.

**2. The reason is that floor area is nearly orthogonal to energy intensity.**

```
corr(log sqm, log mean EUI) = -0.130
=> floor area explains 1.7% of between-building log-EUI variance
```

Dividing by area removes the *unit* problem but almost none of the *intensity*
problem. Buildings differ in what they do, not mainly in how big they are.

**3. Log transformation makes leakage worse, not better.** Both log targets
score *higher* on the identity yardstick than their untransformed counterparts,
because the log compresses within-building temporal variation more than it
compresses between-building differences. Log is not a fix for this problem.

### Where the remaining signal is

Building use carries what area does not — a 12.8× spread with a physically
sensible ordering:

| Primary use | n | Median EUI (Wh/m²/h) |
|---|---:|---:|
| Parking | 22 | 1.64 |
| Lodging/residential | 146 | 9.59 |
| Education | 531 | 12.81 |
| Office | 273 | 14.21 |
| Other | 21 | 14.26 |
| Entertainment/public assembly | 161 | 15.35 |
| Public services | 143 | 16.69 |
| Healthcare | 25 | 20.95 |

This supports the Sprint 3 experiment design directly: `primaryspaceusage` is a
real predictor and belongs in the `M3` (building-attributes) control arm, which
any "spatial" model must be shown to beat.

## 5. Leakage guard

`app/data_engineering/leakage.py` refuses a feature set that identifies
buildings. `lat`/`lng` are permanently forbidden as features — with 14 distinct
pairs they are a site label written in degrees.

`identifiability()` reports what fraction of buildings a feature set pins down
uniquely via its constant-per-building columns. Run against the archived V3
feature set it returns **1.0** — a perfect building index. That is the check
which would have caught the original defect, and it is covered by tests.
